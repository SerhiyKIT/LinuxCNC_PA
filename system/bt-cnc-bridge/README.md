# bt-cnc-bridge: керування LinuxCNC через Bluetooth LE і Wi-Fi

Сервіс на Raspberry Pi, який приймає текстові команди по BLE або по Wi-Fi (TCP,
порт 8765) і передає їх у LinuxCNC через NML (`linuxcnc.stat` / `command` / `error_channel`).
Протокол, PIN і правила безпеки однакові для обох каналів.

- Від власного GUI (`cnc_interface/`) і від заліза міст не залежить.
- Працює паралельно з `bt-wifi-setup` (`CNC-Setup`): у кожного сервісу своя реклама.

## Встановлення

```
sudo bash ~/linuxcnc/configs/LinuxCNC_PA/system/bt-cnc-bridge/install.sh
```

Або офлайн, з картки, вставленої в ПК:

```
sudo bash install.sh --root /media/$USER/rootfs --boot /media/$USER/bootfs
```

Що робить інсталятор:

- копіює модулі в `/usr/local/lib/bt-cnc-bridge/`;
- встановлює `bt-cnc-bridge.service`;
- створює `/boot/firmware/bt-cnc-bridge.txt` з **випадковим PIN** (виводить його на екран), якщо конфігу ще немає;
- вмикає сервіс.

Скрипт можна запускати повторно: наявний конфіг він не змінює.

Сервіс працює від `User=cnc`, root не потрібен. Політика D-Bus BlueZ
(`/usr/share/dbus-1/system.d/bluetooth.conf`, блок `context="default"`) дозволяє будь-якому
користувачу надсилати запити `org.bluez`. Цього достатньо для `RegisterApplication` і
`RegisterAdvertisement`, тому додавати `cnc` у групу `bluetooth` не потрібно.

Діагностика:

```
systemctl status bt-cnc-bridge
journalctl -u bt-cnc-bridge -f
```

Тести (без заліза і BlueZ, потрібен лише pytest):

```
python3 -m pytest system/bt-cnc-bridge/tests -q
```

## Конфіг `/boot/firmware/bt-cnc-bridge.txt`

| Ключ | Типово | Опис |
|---|---|---|
| `NAME` | `CNC-Robot` | ім'я в рекламі (`LocalName`). Alias адаптера міст не змінює |
| `PIN` | випадковий | порожній = без PIN (небезпечно) |
| `ON_DISCONNECT` | `pause` | `pause` \| `abort`: що робити з програмою при обриві з'єднання власника |
| `STATUS_HZ` | `5` | частота `EVT S` (0.5–20), лише при змінах |
| `MAX_JOG_VEL` | `20` | верхня межа швидкості jog joints і осей A B C, град/с |
| `JOG_VEL` | `10` | швидкість інкрементального `jog` / `jogw` для кутів, град/с |
| `MAX_JOG_LIN` | `0.5` | верхня межа jog осей X Y Z, одиниць INI/с (дюйми або мм) |
| `JOG_LIN` | `0.2` | швидкість інкрементального `jogw` для X Y Z, од./с |
| `WATCHDOG_MS` | `500` | таймаут `ping` під час `jogc` |
| `PROJECTS_DIR` | `/home/cnc/ProjectLinuxCNC` | каталог для `ls`/`open`/`file`/`rm` |
| `TCP_PORT` | `8765` | доступ по Wi-Fi; `0` — вимкнути |
| `TCP_BIND` | `0.0.0.0` | інтерфейс для TCP |

Швидкість jog обрізається до меншого з двох значень: `MAX_JOG_VEL` (для X Y Z — `MAX_JOG_LIN`) і `MAX_VELOCITY` з INI (`[JOINT_n]` або `[AXIS_x]`).

Після зміни конфігу: `sudo systemctl restart bt-cnc-bridge`.

## BLE

| | UUID | Властивості |
|---|---|---|
| Сервіс | `a002da01-7653-4ff1-a840-6568658847c6` | |
| RX (клієнт → Pi) | `a002da02-7653-4ff1-a840-6568658847c6` | write, write-without-response |
| TX (Pi → клієнт) | `a002da03-7653-4ff1-a840-6568658847c6` | notify |

Реклама містить ім'я `CNC-Robot` і UUID сервісу. Якщо контролер не приймає повний набір, міст
повторює реєстрацію з меншим: без UUID, потім лише ім'я.

### Кадрування

- Кожне повідомлення в обидва боки — UTF-8 рядок, що закінчується `\n` (`\r` теж вважається кінцем рядка).
- **Pi → клієнт:** довгі рядки ріжуться на пакети під MTU (типово 20 байт, максимум 180) без розриву UTF-8-символів. **Клієнт збирає байти до `\n`.**
- **Клієнт → Pi:** рядок можна писати кількома write. Рядок, довший за 512 байт, відкидається з відповіддю `ERR overflow …`.

### Wi-Fi (TCP)

- Порт `8765` (`TCP_PORT`), той самий протокол і кадрування: рядки UTF-8 з `\n`.
- **Відповіді адресні:** `OK`/`ERR` отримує лише той клієнт, що надіслав команду.
  Події `EVT` отримують усі клієнти, що ввели PIN (і BLE-підписники).
- Обрив Wi-Fi виявляється через TCP keepalive приблизно за 11 с. Обробка така сама, як при обриві BLE.
  Безперервний jog однаково зупиняє watchdog за `WATCHDOG_MS`.
- До 4 TCP-клієнтів одночасно. Трафік не шифрується, тож використовуйте лише в довіреній локальній мережі.

Перевірка з ПК: `nc linuxcnc.local 8765`, далі вводьте команди.

### Кілька клієнтів (BLE)

- Notify з TX отримують **усі** підписані клієнти, бо так працює BlueZ. Відповіді не адресні, тож клієнт має сам зіставляти `OK <cmd>` зі своєю командою.
- Керувати може лише один клієнт, **власник** (`take`). Решта після `pin` бачать статус і можуть виконати `estop on`.
- Клієнт ідентифікується BLE-пристроєм. PIN і власник прив'язані до з'єднання і скидаються при його обриві.

## Протокол v1

**Відповідь на кожну команду:**

- `OK <cmd> [дані]`
- `ERR <код> <текст>`

**Асинхронні події:**

- `EVT S <json>` — статус;
- `EVT E <текст>` — помилка LinuxCNC або подія безпеки.

**Рівні доступу:**

- до `pin` дозволені лише `pin`, `help`, `ver`;
- після `pin` додатково доступні `status`, `take`, `release`, `ping`, `ls` і `estop`;
- решта команд — лише для власника.

| Команда | Дані в `OK` | Опис |
|---|---|---|
| `ver` | `1` | версія протоколу |
| `help` | список команд | |
| `pin <PIN>` | | авторизація. 5 невдалих спроб → `ERR locked` на 60 с (лічильник глобальний) |
| `take` / `release` | | взяти/віддати керування. `release` зупиняє jog |
| `status` | | разовий статус. Сам статус приходить як `EVT S` одразу після `OK` |
| `ping` | | heartbeat. Від власника продовжує watchdog `jogc` |
| `ls` | JSON-масив імен | `*.ngc`/`*.nc` у `PROJECTS_DIR` |
| `estop on\|off` | | `on` дозволено будь-кому з PIN |
| `power on\|off` | | `on` потребує `estop off` |
| `home all\|<J>` | | J: `J0`..`J5` або `0`..`5`. Не чекає завершення хоумінгу |
| `unhome all\|<J>` | | |
| `jog <J> <±крок>` | `J1 5 @5` (крок, швидкість) | інкрементальний jog у градусах зі швидкістю `JOG_VEL` |
| `jogc <J> <+\|-> <швидк>` | `J0 +20` (фактична швидкість) | безперервний jog. **Потрібен `ping` кожні ~200 мс** |
| `jogstop [J\|вісь]` | | без аргументу — усе в поточному режимі (joints або осі) |
| `jogw <X..C> <±крок>` | `X 1 @0.2` | інкрементальний jog у світових координатах (teleop). Потрібен Home |
| `jogwc <X..C> <+\|-> <швидк>` | `C -4` | безперервний jog осі. **Потрібен `ping`**, як для `jogc` |
| `mdi <G-код>` | | потрібні On і homed, інтерпретатор idle |
| `open <файл>` | ім'я | лише ім'я файлу з `PROJECTS_DIR`, без `/`, `\` і `..` |
| `run [рядок]` | | потрібні On, homed і відкритий файл |
| `pause` / `resume` / `stop` / `step` | | `stop` = abort. `step` — з idle або paused |
| `fo <0-150>` / `ro <0-100>` | | feed / rapid override, % |
| `file begin <файл>` | ім'я | почати передачу програми в `PROJECTS_DIR` (ім'я як для `open`) |
| `file data <рядок>` | | наступний рядок програми (може бути порожнім) |
| `file end` | `ім'я розмір` | атомарно записати файл. Максимум 1 МБ; файл, що виконується, не перезаписується |
| `file abort` | | скасувати передачу |
| `rm <файл>` | ім'я | видалити програму з `PROJECTS_DIR` |

**Коди помилок:**

| Код | Значення |
|---|---|
| `unknown` | невідома команда |
| `args` | неправильні аргументи |
| `auth` | потрібен `pin` або PIN невірний |
| `locked` | забагато спроб `pin` |
| `busy` | керування зайняте іншим клієнтом |
| `owner` | спершу `take` |
| `nocnc` | LinuxCNC не запущений |
| `state` | не виконана передумова |
| `path` | заборонене ім'я файлу |
| `nofile` | файл не знайдено |
| `cnc` | LinuxCNC відхилив команду |
| `timeout` | LinuxCNC не відповів |
| `overflow` | рядок довший за 512 байт |
| `size` | програма більша за 1 МБ |

### Статус `EVT S`

Статус надсилається після `take` або `status`, далі з частотою `STATUS_HZ`, але **лише коли щось змінилося**:

```
EVT S {"st":"on","mode":"manual","homed":[1,1,1,1,0,0],"j":[0.0,12.5,-30.0,0.0,0.0,90.0],"prog":"part.ngc","line":12,"run":"idle","fo":100,"ro":100,"ctl":1}
```

| Поле | Значення |
|---|---|
| `st` | `estop` \| `off` \| `on` \| `nocnc` (у стані `nocnc` інших полів, крім `ctl`, немає) |
| `mode` | `manual` \| `mdi` \| `auto` |
| `homed` | 0/1 для кожного joint |
| `j` | позиції joints, градуси, 3 знаки після коми |
| `prog` | ім'я відкритого файлу |
| `line` | поточний рядок руху |
| `run` | `idle` \| `run` \| `paused` |
| `fo`, `ro` | overrides, % |
| `w` | світова позиція X Y Z A B C, машинні координати (без зміщень G54) |
| `u` | лінійні одиниці: `in` або `mm` |
| `ctl` | `1`, якщо хтось має керування |

### Безпека

- **Watchdog.** Якщо під час `jogc` `ping` від власника не приходив довше за `WATCHDOG_MS`, міст виконує `JOG_STOP` і надсилає `EVT E watchdog J<n>`.
- **Обрив з'єднання власника.** Міст зупиняє jog на всіх joints і переводить програму в `pause` або `abort` (за `ON_DISCONNECT`). Керування звільняється, а клієнти отримують `EVT E власник відключився…`.
- **Передумови.** Перед командами міст перевіряє On, homed та idle. Перемикання режимів і teleop робиться через `wait_complete()`. Якщо передумова не виконана, клієнт отримує `ERR state …`.
- **LinuxCNC не запущений.** Відповідь `ERR nocnc`, а перепідключення пробується раз на 2 с.

### Приклад сесії

```
→ pin 123456          ← OK pin
→ take                ← OK take
                      ← EVT S {"st":"estop",...,"ctl":1}
→ estop off           ← OK estop
→ power on            ← OK power
→ home all            ← OK home
→ jog J0 +5           ← OK jog J0 5 @10
→ jogc J1 + 15        ← OK jogc J1 +15
→ ping (кожні 200 мс) ← OK ping
→ jogstop             ← OK jogstop
```

## Структура

| Файл | Призначення |
|---|---|
| `bt_cnc_bridge.py` | точка входу, конфіг, клас `Bridge` (диспетчер команд, таймери) |

| `safety.py` | PIN, власник, watchdog, політика обриву |
| `cnc_backend.py` | обгортка над `linuxcnc` з передумовами і перепідключенням |
| `bridge_constants.py` | UUID, ліміти, коди помилок |
| `tests/` | pytest з моком `linuxcnc` |
